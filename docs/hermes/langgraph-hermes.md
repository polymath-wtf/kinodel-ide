# LangGraph + Hermes: конспект

**Статус:** условная альтернатива при необходимости существующего runtime Kinodel; не базовая архитектура плагина и не решение о миграции. Исходный конспект — 10 октября 2026.
P.S. У меня такое чувство что LangGraph в hermes не нужен, у него достаточно тулов из коробки по дефолту.
А цепочку задач можно сделать например с помощи /goal или kanban.

Актуальная рамка — [hermes-kinodel.md](hermes-kinodel.md). Сначала проверяем native orchestration Hermes по [вопросам](hermes-questions.md). Остальные разделы этого файла описывают только вариант с дополнительным LangGraph, если обнаружен конкретный пробел.

## Вывод

**Если штатных механизмов Hermes недостаточно для выбранного сценария, можно рассмотреть существующий LangGraph Kinodel как исполнитель производственного маршрута.** В этом варианте Hermes выполняет задания специалистов; LangGraph управляет переходами между этапами. Встраивать LangGraph внутрь agent loop Hermes не требуется. Сам факт нодового UI или наличия согласований не доказывает необходимость этого варианта.

```text
React: доска, материалы, параметры, решения автора
                       ↓
Kinodel: версии, задания, результаты генераций
                       ↓
LangGraph: история → утверждение → образы → render → выбор
              ↓                     ↓          ↓
           Hermes                Hermes     worker
```

## Где LangGraph полезен

| Задача | Роль LangGraph |
|---|---|
| Последовательность специалистов | Запускает следующий этап после проверенного результата предыдущего |
| Согласование | Ставит маршрут на паузу через `interrupt`; продолжает после решения автора |
| Возобновление | Сохраняет состояние выполнения через checkpointer | большой **вопрос** как это будет работать в паре с Hermes, главное не оверинжиниринг?
| Несколько независимых задач | Поддерживает параллельные ветки и сбор результатов, когда это понадобится |
| Видимость процесса | Даёт основу для отображения выполненного этапа и точки ожидания |

**Не нужен** для обычного чата, просмотра материалов, ручного изменения prompt/seed и одиночного вызова инструмента. Нодовый интерфейс сам по себе не требует LangGraph.

## Как подключить Hermes

Узел производственного графа:

1. Получает ссылки на точные версии входных материалов и инструкции специалиста.
2. Запускает задание Hermes через API, сохраняет связь задания Kinodel с Hermes run/session.
3. Получает результат и проверяет его по контракту Kinodel.
4. Сохраняет артефакт; возвращает в graph state ссылку, а не весь чат.

Для вызова одного специалиста **не нужен промежуточный продюсер, который решает вызвать `delegate_task`**. `POST /v1/runs` позволяет напрямую передать задание и `instructions`.

Ограничение: произвольные per-request skill/tool allowlist и `output_schema` не подтверждены как единый контракт HTTP run. Для первого опыта — отдельный настроенный profile, зафиксированные инструкции и локальная проверка результата. `output_schema` механизма delegation нельзя автоматически считать возможностью HTTP API.

## Кто управляет маршрутом

- **Hermes-продюсер:** обсуждает замысел, предлагает цепочку, готовит задания.
- **Пользователь:** подтверждает запуск и выбирает материалы.
- **LangGraph/Kinodel:** направляет исполителя на подтверждённый маршрут.
- **Hermes-специалист:** рассуждает внутри назначенного задания. (agent node)

Не давать Hermes и LangGraph независимо продолжать одну производственную цепочку. У Hermes уже есть Kanban/workflow-механизмы, но добавлять их вторым диспетчером поверх LangGraph не нужно.

## Перегенерация без агента

```text
Кадр → изменить prompt/seed → новое render-задание → новый вариант
```

Это прямая команда Kinodel к worker/provider. **Ни Hermes, ни новый большой запуск графа для неё не обязательны.**

Hermes нужен, если правка смысловая: «сделай тревожнее, сохрани героя». Он предлагает параметры; рендер выполняется контролируемым инструментом. Старый вариант сохраняется, новый не становится утверждённым автоматически.

## Что сохранить из текущего backend

| Сохранить | Зачем |
|---|---|
| LangGraph и существующий механизм продолжения | Не писать новый workflow engine |
| Контракты и валидацию артефактов | Принимать результаты Hermes в существующем формате |
| Версии и согласования | Знать, какой материал выбран автором |
| Учёт заданий, попыток и внешних заказов | Восстанавливать работу без слепого повторного submit |
| Workers/provider adapters и чтение originals | Генерировать и показывать материалы напрямую |

**Добавить:** мост Hermes и приём его результатов. Сначала заменить исполнение одного специалиста внутри текущего backend. Извлечение отдельного «нового ядра» пока не обосновано; связанность модулей для такого переноса детально не проверена.

## Граница гарантий

- LangGraph checkpoint **не заменяет** версии материалов, receipts заказов и approval конкретной ревизии.
- При resume узел может выполниться заново: внешний вызов должен учитывать уже сохранённое задание/результат.
- Hermes поддерживает `Idempotency-Key` для `/v1/runs`, но это ограниченная дедупликация приёма запроса, не гарантия однократного выполнения всех tools.
- Неизвестный исход Hermes run — повод выяснить состояние, а не автоматически запускать нового специалиста.
- Остановка агента не доказывает отмену отправленного рендера.

## Минимальная проверка идеи

1. **Бриф → Hermes Storytell → сохранённый артефакт.** Проверить формат, reload и повтор доставки.
2. **Story → решение автора → Hermes Wardrobe** через существующий LangGraph. Проверить точную ревизию входа и продолжение после рестарта.
3. **Изменить seed → новый render** без модельного вызова. Сохранить старый результат; повтор запроса не создаёт второй заказ.

Если этот цикл работает проще текущего, расширять доску. React-плагин/оболочку Hermes можно упаковать отдельно: способ размещения UI не меняет роль LangGraph.
