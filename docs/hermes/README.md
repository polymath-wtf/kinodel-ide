## Зачем это автору

Автор говорит продюсеру: «Хочу короткую историю про курьера Лину в ночном городе». Продюсер помогает собрать маршрут: история → образы → кадры → видео → сборка. На доске видны специалисты, их задания, сохранённые результаты и места, где нужно решение автора.

Идея: **Kinodel отвечает за творческое рабочее пространство и материалы, Hermes — за работу специалистов, инструменты и разговоры.** Это позволяет не строить заново универсального ассистента, веб-поиск, управление контекстом и весь набор инструментов. Но управление версиями и безопасное продолжение производства не исчезают вместе с заменой агента.

## Что есть сейчас

В Kinodel уже построены Story → Wardrobe, сохранение результатов и согласования. Один portrait проверен live; последовательные image units, общий Continue и просмотр originals приняты в ограниченных offline/mock/browser сценариях. Следующая живая проверка portrait → background → sheet ещё впереди. Полное производство с раскадровкой, видео, монтажом и произвольным конструктором не готово. Источник статуса — [Local MVP](../roadmap-mvp.md) и [ComfyUI roadmap](../roadmap-comfyui.md), а не этот концепт.

В актуальном upstream Hermes существуют собственный агентный runtime, сабагенты, локальные сессии и память, skills, инструменты, официальный Desktop и несколько способов расширения. Наличие этих механизмов проверено по документации и исходникам; их совместная работа с Kinodel и наличие всех функций в конкретном установленном релизе не проверены. Подробности и источники — [исследование](research.md).

## Проверка исходной идеи

| Предложение | Что получит автор | Что ещё потребуется |
|---|---|---|
| React-плагин с нодовой доской | Собирает и читает маршрут визуально | У Hermes есть Desktop SDK и dashboard extensions. Это разные системы; готового Kinodel-конструктора они не дают |
| Цепочки из skills и мультиагентов | Назначает специалистам инструкции и связывает результаты | Skill — инструкция, не исполняемый узел с входами, выходами и восстановлением. Обвязку создаёт Kinodel |
| Вайбкод маршрутов | Продюсер предлагает подходящую цепочку вместо ручной настройки каждого случая | Сгенерированный маршрут сначала черновик. Проверка связей, инструментов, результата и подтверждение запуска обязательны |
| Агент дописывает недостающую функцию | Может подготовить новый skill, узел или код адаптера | Изменение кода — отдельная задача разработки, не самовольная модификация работающего производства |
| Быстрый вход через Hermes Desktop | Не настраивает ещё одного универсального ассистента | SDK существует. Установка Kinodel, запуск его сервиса и совместимость с релизами требуют отдельной проверки |
| Память о вкусе автора | Повторно использует согласованные предпочтения и приёмы | Память Hermes и изменяемые skills не заменяют библиотеку принятых решений. Автосохранённый вывод агента — ещё не вкус автора |
| Только Kinodel-чаты в отдельном окне | Личные разговоры не засоряют проект | Нужны отдельный profile и явные связи project ↔ session ↔ run; внешний вид окна сам по себе не изолирует память |
| Меньше backend | Переиспользует модельные подключения, tool runtime и conversation lifecycle | Остаются версии, валидация, согласования, зависимости и учёт платных заказов. Размер экономии пока не измерен |
| Structured output между нодами | Следующий специалист получает выбранные поля, а не всю беседу | `delegate_task` поддерживает `output_schema`, но возможен невалидный результат. Kinodel повторно проверяет его перед сохранением и передачей |
| HTTP, интернет, ComfyUI | Специалист сам находит справку и готовит генерацию | Возможности есть; у ComfyUI это optional skill со скриптами REST/WS. Заказ, отмена и повтор платного рендера требуют отдельного контроля |
| Продюсер передаёт правки специалистам | Общий чат остаётся точкой входа, у ноды можно открыть разговор | Live steering и чтение child-чатов существуют, но зависят от транспорта и подключения. «Любому старому сабагенту можно написать» не подтверждено |
| Сжатие основного контекста | Длинный проект не требует бесконечного промпта | Документированная команда — `/compress`, не `/compact`. После сжатия точные версии и решения восстанавливаются из материалов проекта |
| Анализ музыки и других медиа | Получает полезный результат без просмотра огромного JSON | Hermes упрощает применение инструментов, но извлечение битов требует конкретного анализатора. Большие данные храним в файле; в чат выдаём краткую сводку и ссылку |
| Комьюнити и продвижение | Легче обнаружить продукт в знакомой экосистеме | Это продуктовая гипотеза, не подтверждённый канал продаж или доказанная экономия поддержки |

## Что именно означает «плагин»

Есть три разных варианта оболочки: Python-плагин добавляет инструменты и hooks; web-dashboard extension — вкладку в браузерном dashboard; Desktop SDK — страницы и панели в официальном Electron-приложении. **React-интерфейс можно сделать официальным расширением**, а не обязательно форком Hermes.

В первоначальном варианте интеграции рассматривалось отдельное localhost-окно для переиспользования React Kinodel, затем тонкая Desktop-оболочка. Для минимального плагина выбор оболочки открыт до discovery существующих SDK и целевой установки. Встраивание через `SandboxedFrame` возможно, но его изоляция ограничивает storage и доступ к host SDK; перенос существующего приложения в iframe не считается готовым решением. Для полноценной native-страницы отдельно проверяем сборку нодового UI: disk plugin не принимает JSX и произвольные imports напрямую.

## Как устроен Hermes под капотом

У Hermes Python-backend с собственным циклом: модель получает задание → выбирает инструмент → получает результат → продолжает или отвечает. LangGraph не является основой этого core runtime. Сервисы, tool registry, сессии и API уже есть; Kinodel не обязан повторять их целиком.

Указанная в вопросе boolean state machine управляет **разговором**, а не производственным маршрутом: сохранить ли текущую сессию, создать ли новую, продолжить ли прерванный turn. Например, после аварии gateway может продолжить разговор, но это не означает «утверждён второй дубль третьего шота, первый заказ видео уже оплачен, повтор запрещён».

Отдельный журнал Hermes сохраняет результаты background delegation, однако незавершённые дочерние задачи после смерти владельца могут стать `unknown`; старый worker не восстанавливается автоматически. HTTP runs и messaging gateway имеют разные правила продолжения. Нельзя переносить гарантию одного транспорта на другой.

## Как превратить skill в ноду
p.s. нужно продумать structured input и structured output.

Нода — **сохранённое задание специалисту с проверяемым результатом**, а не просто ссылка на `SKILL.md`. Для неё нужны выбранные входы, версия инструкций, допустимые инструменты и формат результата. Связь между нодами говорит, какой конкретный результат передать дальше.

Пример: «История» возвращает название, логлайн и сцены. «Образы» получает выбранную версию истории. Связь может передать `story.characters` в `wardrobe.characters`; нода «Константа» задаёт формат кадра. Проверка должна остановить маршрут, если поле отсутствует или результат не соответствует формату. Универсальный n8n-подобный язык выражений для первой проверки не нужен.

Начальные типы: **специалист**, **решение автора**, **инструмент генерации**, **сохранённые данные/константа**. Позже — ветвления и параллельные группы, когда появится реальный сценарий. Ноды Hermes не нужно «переводить на язык LangGraph»: Hermes вызывается через API внутри нужного шага.

## Есть ли роль для LangGraph

| Вариант | Что видит автор | Ограничение |
|---|---|---|
| Hermes ведёт свободную творческую сессию | Продюсер импровизирует, делегирует и предлагает материалы | Доска может быть планом и журналом, но не гарантированно исполняемым маршрутом. Для такого прототипа LangGraph не обязателен |
| Kinodel исполняет маршрут, Hermes выполняет агентные задания | Понятны зависимости, согласования и точка остановки | Нужен слой управления производством. Существующий LangGraph можно сохранить; правила версий и заказов всё равно принадлежат Kinodel |
| Hermes и LangGraph независимо управляют всей цепочкой | Два диспетчера пытаются продолжать один проект | Не рекомендуется: конфликт владельцев, повторные задания и непонятная отмена |

**Первоначальный вариант: Hermes как творческая команда, Kinodel как производственная память и контроль.** Существующий LangGraph можно рассмотреть при интеграции со standalone backend. Для минимального плагина это не рекомендация по умолчанию: сначала проверяем, что обеспечивают native orchestration, tools и хранение Hermes; дополнительный runtime оправдывается только конкретным пробелом.

LangGraph даёт отметки исполнения и паузы, но тоже не обеспечивает автоматически отсутствие повторной оплаты: при восстановлении узел может выполняться заново. Вызов Hermes, сохранение результата и внешний заказ должны опираться на сохранённые идентификаторы работы и проверяемые receipts.

## Где хранить проект

Markdown wiki подходит для замысла, визуальной библии, заметок, вкуса автора и связей между знаниями. Медиа живут рядом отдельными файлами; для больших таблиц, таймингов и планов допустимы структурированные файлы. Поиск и чанки можно добавить позже — это пересоздаваемые представления, не единственный архив проекта.

**Предлагаем не превращать wiki в единственную операционную базу.** Ответы на «какая версия принята?», «какой заказ уже отправлен?», «кто сейчас работает?» требуют безопасных записей при конкурирующих действиях и перезапуске. Hermes сам хранит разговоры и служебное состояние в SQLite. Для Kinodel разумно переиспользовать существующий локальный учёт, а не изобретать транзакции в Markdown.

Разделение: wiki — человеческий смысл; сохранённые версии — творческая истина; небольшой журнал — выполнение и заказы; Hermes session store — беседы. Не нужно дублировать всю базу Hermes в Kinodel. Ссылки на profile/session/run связывают слои. Skills меняются между запусками; работающий запуск сохраняет точную версию использованных инструкций.

## Продюсер и правки

Продюсер может предложить новую цепочку, объяснить последствия правки и оформить задание точному владельцу. Но он не всеведущий читатель всех чатов: child получает отдельный контекст, а родитель обычно видит результат. Доступ к подробной беседе даётся явно через поддерживаемый интерфейс.

Вот например как можно сделать, пользователь общается с продюсером, тот даёт команду специалисту, тот выполняет и возвращает результат который записывается в артефакт (типа список задач на киностудии). Если пользователь хочет внести правки, он может сделать это через продюсера, который затем передаст команду специалисту.

Автор пишет «Лина должна быть в красной куртке». Создаётся новая версия образа. Прежние кадры остаются доступны, но помечаются как использующие старый образ; новые кадры можно запустить от нового выбранного входа. **Не обещаем автоматическую пересборку всех шотов.** Live steering — замечание выполняющемуся специалисту, а правка принятого материала — новое задание и новая версия.

Разделение чатов и доступ основного Hermes к проектам — два отдельных решения. В Kinodel показываем только связанные с ним сессии. Основному Hermes можно явно открыть чтение библиотеки через tool/MCP, но не давать автоматический доступ ко всем приватным беседам и прямую запись утверждений.

## Альтернативная архитектура: интеграция с текущим backend

```text
Автор → React Kinodel: доска + продюсер + просмотр материалов
                    ↓
           Локальный сервис Kinodel
           ├─ версии, проверки, решения автора, учёт работы
           ├─ wiki и библиотека файлов
           └─ мост → Hermes API: отдельный profile, sessions, runs

При production-запуске: маршрут Kinodel/LangGraph → задание Hermes
При работе продюсера: Hermes → узкие инструменты Kinodel → тот же контроль
```

Сначала HTTP API + SSE для общего чата, заданий и истории. Token Hermes остаётся в локальном сервисе. Сервис слушает loopback и проверяет доступ; «localhost» не означает отсутствие рисков. Для живого управления дочерними чатами отдельно проверить RPC: HTTP steering основного run не равен child steering.

Генерации запускаются через один учитываемый инструмент Kinodel, а не одновременно через его worker и свободный terminal Hermes. Python plugin или MCP нужны только если продюсеру действительно требуется вызывать операции Kinodel; не внедряем оба сразу. Profile разделяет память и настройки, но не является sandbox для файлов.

## Возможные дополнения для standalone-интеграции

Ниже — scope первоначального варианта с текущим backend. Для native-плагина каждый пункт сначала сопоставляем с готовыми механизмами Hermes; это не обязательный список собственных компонентов.

1. Доску и минимальное описание маршрута: задания, выбранные входы, результаты, связи и решения автора.
2. Мост Hermes: запуск, события, история, связь проекта с сессией, обработка потери соединения и неопределённого завершения.
3. Приём результата: строгая проверка, сохранённая версия, точный владелец и происхождение. Без этого JSON из сабагента нельзя безопасно передавать дальше.
4. Контроль производства: согласования версий, зависимости, отмена, разрешённое продолжение и сверка платных заказов.
5. Упаковку плагина, проверку совместимости с Hermes и ограничение инструментов/файлов. Доступ к локальному диску не должен означать произвольную перезапись библиотеки.

Пункты 3–4 частично уже построены в Kinodel. Эксперимент должен показать, какие из них можно переиспользовать без переноса всего backend. Нельзя заранее обещать «только frontend и несколько строк backend» или точное ускорение MVP.

## Как проверить идею, не начиная переписывание

Это исторические предложения для standalone-интеграции, не новый first-build roadmap и не scope native-плагина. Актуальный кандидат MVP — [hermes-mvp.md](hermes-mvp.md); прежде чем выбирать эксперименты ниже, проверяем штатные механизмы Hermes.

**Проверка 1 — окно и один специалист.** Выбрать точный релиз Hermes; проверить capabilities. Передать вымышленный бриф и один skill, получить проверяемую историю, сохранить её и открыть после reload. Личный чат Hermes не появляется в проекте. Ошибочный output блокирует передачу дальше. Повтор доставки сохранённого задания не создаёт ещё одну опубликованную версию; неопределённый исход не вызывает тихий повтор модели.

**Проверка 2 — маленькая цепочка.** История → решение автора → образы. Разрешить выбор двух специалистов и связь выбранных данных; продюсер может предложить черновик того же маршрута. Изменение истории создаёт новую версию, а не подменяет вход выполняющегося задания. Просмотр сохранённого child-чата проверяется при наличии поддерживаемого доступа; возможность писать живому child — отдельная проверка транспорта, не обязательство первой версии.

**Проверка 3 — один контролируемый render.** Подключить существующий учёт генерации Kinodel. Закрыть UI и перезапустить компоненты на опасных границах; сохранить и повторно открыть заказ/результат без нового submit. При неизвестном исходе сначала сверить заказ. Дублирующий UI-запрос и поздний результат после отмены не должны продвигать маршрут.

Продолжать к Desktop packaging и расширенному конструктору, только если первые проверки показывают реальное переиспользование, удобный авторский сценарий и приемлемую сложность моста. Полный video/editor, произвольные плагины нод, swarms, vector DB и автообновление работающих маршрутов пока вне эксперимента.

## Какое решение требуется

**Поддержать исследовательскую ветку «Kinodel Studio на Hermes», не объявляя миграцию.** Первый вопрос: можно ли сделать один полезный авторский цикл существенно проще — бриф, специалист, сохранённый результат, правка — без потери материалов и смешивания чатов?

Если да, переносим вторую задачу и проверяем производственную границу. Если новый мост требует постоянного доступа к приватным internals или восстанавливает почти весь Hermes runtime заново, ограничиваем его роль общим продюсером/ассистентом. Текущую проверенную систему не удаляем по результатам чтения документации.
