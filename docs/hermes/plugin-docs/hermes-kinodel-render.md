# Render: от плана к изображениям и клипам

**Статус: цель препродакшна Hermes × Kinodel.** Автор выбирает условия генерации, получает дубли и утверждает набор для следующего этапа. Render отвечает за проверку заказа, обращение к провайдеру и сохранение оригиналов; творческий план готовит специалист.

## ComfyUI по умолчанию, fal.ai — явная альтернатива

Для MVP основной путь и default **изображений и видео — ComfyUI**. Автор подтверждает его в Brief; fal.ai остаётся явной альтернативой при настроенной совместимой интеграции, не автоматическим fallback. Профиль фиксирует фактического провайдера, модель/workflow и возможности.

В snapshot Hermes уже документированы `image_generate` и `video_generate`, а **FAL входит в bundled providers**. Это не доказывает наличие ключей и работоспособность выбранной модели в нашей установке. ComfyUI описан как optional skill: это полезные инструкции и скрипты, но не подтверждённый установленный provider adapter. Подключение ComfyUI к общему проверяемому пути image/video — отдельный пробел реализации, который нужно закрыть. Внешний ручной workflow не заменяет этот продуктовый путь.

Штатный выбор провайдера идёт через конфигурацию Hermes. Связь замороженного профиля конкретного запуска с фактическим вызовом ещё нужно обеспечить и проверить: LLM не выбирает backend, модель или платный тариф вместо автора.

## ComfyUI-профиль по умолчанию

За основу берём уже подготовленные workflows из [ComfyUI Tool](../../tools/comfyui-tool.md):9–33. Переиспользуем файлы и явные mappings, не переносим старый runtime или V2 schema. Указанные ID — имена профилей старого registry, которые предстоит подключить к Hermes.

| Применение | Default workflow / файл в `workflow/comfyui/` | Входы |
|---|---|---|
| Portrait и location: txt2img | Krea2, `krea2-txt2img` — `txt2img krea2 api v1_local.json` | Prompt, width/height, seed; без render image refs |
| Character sheet: img2img | Qwen, `qwen21-multi-img2img` — `qwen img2img api v1.1 3img.json` | Два отдельных входа строго `[portrait, location]` |
| Кадры раскадровки: img2img | Тот же Qwen multi template | Для основного character shot `[portrait, character_sheet, location]`; другие роли/число refs требуют явной совместимой конфигурации |
| Видео: img2vid | MiniMax H3, `minimax-h3-img2vid` — `minimax img2vid api v1.json` | Точный выбранный storyboard frame как first-frame input и motion prompt |
| #future: ref2vid | MiniMax H3, `minimax-h3-ref2vid` — `minimax ref2vid api v1.json` | `[storyboard_frame, portrait, character_sheet]`; вне MVP, без обещания точного frame 0 |

### Три обязательные опоры MVP

Ровно **один logical unit каждого вида: portrait, location, character_sheet**. Первоначальная генерация создаёт по одному кандидату на unit; ручные дополнительные дубли не увеличивают число ролей. Portrait и location генерируются txt2img. Затем sheet генерируется img2img с **обоими** сохранёнными originals, не коллажем:

```text
portrait (Krea2 txt2img) ─┐
                        ├→ character_sheet (Qwen img2img)
location (Krea2 txt2img) ─┘
```

В старой карте роль `background` соответствует нашему `location` — это mapping, а не четвёртый anchor. Location показывает среду без персонажа. До sheet-submit фиксируются exact parent candidate refs/digests. При смене portrait или location нужен новый совместимый sheet; нельзя утвердить sheet от других parents. Review принимает один полный набор из трёх выбранных изображений. Многоперсонажное/многолокационное покрытие не расширяем автоматически: scope и явный выбор обсуждаются в Brief.

### Ограничения, найденные в исходной настройке

- Qwen multi использует отдельные `LoadImage` inputs и mapping для 1/2/3 изображений. Для sheet нужно два входа, однокартинный Qwen template не подходит. Текущий standalone registry допускает только square 512/768/1024; прямоугольные размеры для этой настройки не обещаем без новой проверки.
- Krea2 txt2img mapping передаёт размеры непосредственно; исходный registry также допускает 768×1024 и 1024×768. Общие размеры проекта всё равно должны подходить всем выбранным image workflows.
- MiniMax img2vid связывает LoadImage с `first_frame`. Формула числа кадров, RIFE и output FPS могут дать длительность, отличную от введённых секунд: замерить готовый MP4 и согласовать допуск, не объявлять поле duration гарантией длины.
- Исходный MiniMax graph подключает audio к output. Текущий контракт финала требует отсутствия audio stream; явно согласовать его обработку в adapter/Montage и проверить `ffprobe`, не называть исходный клип автоматически немым.
- В старом проекте preparation-enabled — txt2img и Qwen multi; video обозначен inspection-only. Настройки существуют, но это не означает, что весь этот путь уже проверен live или подключён к Hermes.

Endpoint/auth остаются конфигурацией, node IDs и workflow digests — adapter mapping. Новый plugin должен подтвердить installed schemas и исходные файлы; при несовместимости возвращает ошибку, не исправляет окружение агентом.

## Автоматически и вручную — один заказ

В маршруте специалист сохраняет план, после чего генерация запускается автоматически в пределах разрешения автора. В инспекторе автор может изменить prompt и поддержанные настройки и нажать Render **без обязательного LLM-вызова**. Оба действия проходят один путь: проверка входов и возможностей → сохранение заказа → вызов совместимого инструмента/адаптера → импорт и проверка оригиналов.

Каждый новый творческий запрос создаёт новый candidate — дубль. Старые планы, заказы и дубли сохраняются; ручные overrides видны отдельно и не переписывают исходный план. Просмотр и выбор дубля сами по себе ничего не генерируют.

## Что фиксируем перед генерацией

| Условие | Договорённость |
|---|---|
| Содержание | Точный plan revision, prompt, роли и порядок refs, выбранные parent candidates, версия профиля/workflow |
| Настройки | Фактическая модель и поддержанные параметры. Seed, CFG и steps показываем и передаём только там, где они работают; неизвестное значение не выдаём за зафиксированное |
| Размер | Качество `480p`, `720p`, `1K` разрешается профилем в конкретные **W×H** с выбранным aspect ratio. У `1K` нет единого значения для всех моделей |
| Видео | Порядок шотов, запрошенная и согласованная длительность каждого клипа; после получения — измеренные размеры и длительности |
| Результат | Оригинальные bytes, digest, связь с заказом/попыткой и unit; provider URL или cache не заменяет проектный оригинал |

Базовый режим — **MiniMax H3 img2vid от точного выбранного кадра шота**. Ref2vid оставлен в #future. Обязательные anchor roles и их зависимости определены выше; agent plan заполняет их prompts и bindings, не меняет topology.

Общая длина фильма — сумма полных клипов по шотам. Провайдер может предлагать только дискретные длительности: например, требуемые 6 секунд нельзя молча заменить доступными 5 или 10. До заказа согласуем поддержанный вариант и обновлённую общую длину. Аналогично согласуем изменение размера/aspect; неподдержанные refs и настройки не отбрасываем молча. Возвращённые metadata сверяем с оригиналом.

## Выбор и согласование

Для каждой обязательной unit — образа, кадра или клипа — автор выбирает **ровно один дубль**, затем отдельно утверждает полный совместимый набор. Последний созданный дубль не становится выбранным автоматически. Проверяем покрытие, порядок и точные родительские связи: клип от кадра A нельзя принять как клип от кадра B.

Изменение утверждённого предка после фиксации prepared input зависимой операции создаёт новое связанное производство — даже если следующий worker ещё не запущен. Прежние результаты остаются доступными, но не получают approval для новых входов. Правила — [граница правок](hermes-artifact.md#граница-правки-фиксация-входов-следующей-операции).

## Повтор, остановка и оплата

До внешнего вызова сохраняем логический заказ, точные входы, настройки и разрешённую попытку; после принятия — receipt/job ID и известный статус. Повтор доставки, перезапуск или повторный клик возвращают сохранённый заказ/результат, а не создают новый платный submit. Успешные units переиспользуются.

Если исход submit неизвестен, состояние **blocked: требуется сверка с провайдером**. Сначала reconciliation по доступным средствам, без слепой повторной отправки и обещания exactly-once. Остановка агента или сессии не доказывает отмену provider job; фактическую отмену и завершение отслеживаем отдельно.

Учёт минимален: явное разрешение запуска и его области, допустимые настройки и число попыток; используем поддержанные host-лимиты стоимости/попыток. Новая платная попытка требует остатка разрешения либо нового согласия. Continue и restart лимиты не обновляют. Недостающие сведения сохраняем узко по операции, без нового общего budget engine; неизвестное разрешение или исход заказа блокирует вызов.

## Сборка немого фильма

FFmpeg через существующий `terminal` и подходящий установленный skill собирает **утверждённые полные клипы в порядке шотов**. Это детерминированная сборка по сохранённому списку, без творческого LLM-монтажа, скрытой обрезки и переходов. При необходимости явно нормализуем технические форматы. Итог — финальный ролик mp4; `ffprobe` проверяет читаемость, размеры, длительность суммы клипов с учётом точности контейнера и отсутствие audio stream. Оригиналы и рецепт сборки сохраняются.

Цель приёмки: оба настроенных провайдера выбираются явно; автоматический и ручной запросы используют общие проверки; после перезапуска нет повторного submit, сохранённые оригиналы доступны без провайдера, финальный файл соответствует утверждённому набору. Эти проверки ещё предстоят.
