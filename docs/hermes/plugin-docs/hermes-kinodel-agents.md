# Съёмочная группа Kinodel

**Статус:** целевые роли и рабочие процессы до реализации. Пять агентов: **Producer, Storytell, Wardrobe, Storyboard, Filmmaker**. Montage — детерминированный инструмент, не шестой агент. Наличие инструмента в документации Hermes не доказывает его доступность в целевой установке.

## Producer — основной собеседник автора

Producer обязателен в препродакшне и остаётся основным чатом для последующей обратной связи. Он читает референсы, уточняет историю, персонажей и локацию. После опроса упаковывает ответы в полный `brief.json`; последующие изменения сохраняет как `brief_v1 → brief_v2 → brief_v3`. До упаковки незакрытые вопросы живут в беседе, отдельного draft-артефакта нет.

До запуска Producer собирает и показывает автору:

- замысел, стиль, персонажей, место действия и выбранные референсы;
- полную длительность фильма и число шотов;
- ширину/высоту изображений и соотношение сторон;
- качество видео и provider/profile отдельно для изображений и видео: по умолчанию ComfyUI — Krea2 txt2img, Qwen img2img, MiniMax H3 img2vid; fal.ai выбирается явно как альтернатива, ref2vid отложен.

Предложение значения не означает согласие автора. Несовместимые параметры требуют уточнения; скрыто менять размеры, длительность, число шотов или провайдера нельзя. Автор явно подтверждает итоговый бриф и запуск. Это отдельное решение перед четырьмя производственными gates.

После запуска Producer объясняет текущий результат и помогает сформулировать замечания. Запрос правок привязывается к конкретной review-версии и направляется её владельцу через plugin-действие. Producer не утверждает материалы за автора, не заменяет специалиста и не меняет фиксированный маршрут. Задания создаёт workflow; workers запускает Kanban dispatcher, без ожидания внутри turn Producer.

## Кто делает результат

| Агент | Работа и последовательность | Минимально нужные инструменты |
|---|---|---|
| Producer | Уточнить идею → собрать Brief → показать точную версию → получить подтверждение; позднее выпускать Brief revisions и помогать с feedback. | Разрешённое чтение материалов, `skill_view`, `vision_analyze`. Предлагаемые plugin-действия: сохранить Brief revision, запросить правку конкретного результата. Общий `delegate_task` и произвольное создание Kanban tasks не нужны. |
| Storytell | Прочитать подтверждённый бриф → построить историю → описать упорядоченные шоты и действие → выдать полную версию для story review. | `read_file`, `skill_view`; `vision_analyze` только при необходимости понять визуальный референс. Предлагаемое plugin-действие: сохранить результат истории. Рендер не нужен. |
| Wardrobe | Прочитать **полную approved Story и Brief** → вернуть план ровно трёх опор: portrait, location, character_sheet. Первые две txt2img; sheet img2img использует обе. Workflow генерирует набор и открывает review. | Разрешённое чтение, `skill_view`, `vision_analyze`; контролируемая публикация плана. Image tool/ComfyUI adapter вызывается общим render-путём. |
| Storyboard | Прочитать **полную approved Story и Brief**, approved anchors → спроектировать начальную композицию каждого шота → вернуть prompts и точные refs. Workflow генерирует frames и открывает review. | Разрешённое чтение, `skill_view`, `vision_analyze`; контролируемая публикация плана кадров. Генерация выполняется tool-частью этапа. |
| Filmmaker | Прочитать **полную approved Story и Brief**, approved frames → вернуть план движения/камеры и длительностей непрерывных клипов. Workflow генерирует videos и открывает review. | Разрешённое чтение, `skill_view`, `vision_analyze`; контролируемая публикация видеоплана. Video tool/ComfyUI adapter вызывается общим render-путём. |

У каждого специалиста одна зона ответственности. Wardrobe не переписывает историю, Storyboard не переизобретает утверждённую внешность, Filmmaker не меняет утверждённую композицию молча. Нужное изменение чужого входа возвращается автору как вопрос с последствиями.

## Инструменты: документированное и предлагаемое

`delegate_task`, `read_file`, `skill_view`, `vision_analyze`, `image_generate`, `video_generate`, `terminal` — существующие **документированные** инструменты Hermes. Их доступность, параметры и capabilities требуют проверки установки. `skill_view` нужен для загрузки подходящих инструкций; этот документ не задаёт вымышленных имён установленных skills.

Сохранение Brief/плана/полной версии, передача feedback, контролируемый заказ рендера, выбор кандидата и approval — **НОВЫЕ предлагаемые действия plugin**. Это семантические требования к будущим инструментам и UI-командам, не имена уже зарегистрированных API. Selection и approval принадлежат автору, не агенту.

Автоматическая генерация по плану агента и ручной Generate используют общий путь: проверка входов и поддерживаемых настроек → разрешение и учёт операции → вызов провайдера → сохранение результата. Агент не обходит его прямым неучтённым вызовом генератора. Ручной запрос идёт по этому пути **без LLM**. Не требуется удерживать творческий LLM turn всё время рендера; механизм ожидания и восстановления нужно определить отдельно.

`terminal`, редактирование кода/окружения и произвольное делегирование исключены из tools творческих workers. Технический путь Montage выполняет фиксированную сборку через доступные средства host; это не доступ специалиста к shell. Montage получает выбранные approved clips, соединяет их в Story-порядке и выдаёт проверенный MP4; творческий агент и новое согласование для этого не нужны.

## Делегирование и правки

Производственные специалисты запускаются как Kanban workers заданных профилей. Они не являются дочерними вызовами, которых Producer должен ждать через `delegate_task`. Маршрут и зависимости определяются [контрактом нод](hermes-nodes.md); task skills/model задаёт workflow. Штатный public child lifecycle требует active parent и не подменяет выбранный Kanban lifecycle.

При feedback текущего review владелец получает предыдущий полный результат, утверждённые входы и замечания; возвращает **новую полную версию**, а не фрагмент, который автор должен собирать вручную. Если данных не хватает, задаёт вопрос. Если изменяемый результат уже закреплён в prepared input зависимой операции, Producer объясняет необходимость нового производства — даже если следующий worker ещё не стартовал. Автоматической пересборки старого нет.

## Контекст и границы

Замечание можно отправить напрямую из панели специалиста. Пользователь проверил возможность продолжать прежнюю worker session внутри Kanban lifecycle; точный механизм и ограничения уточним у Hermes. При rework всё равно передаются точные входы и предыдущий результат, а не только старый transcript. Подробности — [артефакты](hermes-artifact.md#напрямую-специалисту-и-в-его-рабочий-чат).

Каждый worker принимает structured input и возвращает `completed` с полным output, `needs_input` с вопросами либо `failed` с причиной. Ответ и артефакт содержат `created_by` с агентом/профилем и фактическими host IDs. Schemas и bindings — [контракт данных](hermes-artifact.md). `completed` не означает approval: plugin отдельно валидирует результат. Отсутствующая модель, ошибка workflow или неверный файл не разрешают чинить установку, писать код, менять провайдера или выполнять чужую задачу. Канонический результат при ошибке не меняется.

Минимальный набор tools ограничиваем средствами host/profile/plugin; prompt дополняет, но не заменяет ограничение. Проверить отдельно встроенные Kanban tools создания задач: отключение auto-decompose само по себе их не убирает.

Каждый агент получает только нужные для задачи версии, выбранные автором references и инструкции своего ремесла. Подготовленный контекст, наблюдаемая загрузка skill и недоступные внутренние данные различаются; private reasoning и полная лента child-tools не обещаются.

Поведение экрана — [Web UI](hermes-webui.md), входы/выходы и четыре gates — [ноды](hermes-nodes.md), версии и решения — [артефакты](hermes-artifact.md), backend lifecycle — [архитектура](hermes-kinodel-architecture.md).

Детали — [render](hermes-kinodel-render.md) и [контекст](hermes-kinodel-context.md). Ограничения Hermes сверяются по [delegation](../hermes-docs/backend/delegation.md) и [public child lifecycle](../hermes-docs/backend/subagent-lifecycle-api.md); это документальные основания, не подтверждение реализации Kinodel. Model-facing `delegate_task` наследует tools родителя: ограничение набора нужно обеспечить поддерживаемой plugin/profile-поверхностью, а не только фразой в prompt.
