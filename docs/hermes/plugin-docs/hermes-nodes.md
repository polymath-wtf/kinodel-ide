# Ноды: результаты и переходы производства

**Статус:** целевой контракт до реализации, не установленная Hermes schema. Документ владеет типами нод, входами, выходами, зависимостями и разрешёнными переходами. [UI](hermes-webui.md) описывает представление, [агенты](hermes-kinodel-agents.md) — работу специалистов.

## Типы и фиксированный маршрут

- **Agent** рассуждает и создаёт полную творческую версию своего результата.
- **Tool** выполняет проверяемое действие: рендер или детерминированную сборку.
- **Review** сохраняет явное решение автора о конкретной версии.

Это логические роли. Одна экранная карточка этапа может объединять Agent → Tool → Review; отдельный runtime-класс, task или child на каждую карточку не требуется.

Исполнение выбрано через **Hermes Kanban**: одна task на производственный этап, attempts для доработок до завершения. Task создаётся plugin workflow при допуске этапа; будущие карточки Pipeline пока являются представлением шаблона. Канонические входы/выходы и видимые field bindings определены в [артефактах](hermes-artifact.md). Связи фиксированы, агент не выбирает следующий edge.

**Препродакшн → подтверждённый бриф → Storytell → story review → Wardrobe + anchors → anchor review → Storyboard + frames → frame review → Filmmaker + videos → video review → Montage → final silent MP4.**

Четыре производственных gates: история, anchors, frames, videos. Подтверждение брифа разрешает запуск отдельно; планы не добавляют обязательных согласований. Готовность final — техническое завершение, не пятый gate.

## Входы, выходы и зависимости

Последовательность детерминирована правилами. `failed` останавливает этап с ошибкой, `question` — с вопросом автору. Worker не создаёт обходные задачи, не меняет tools/provider и не исправляет код/окружение. Автоматическая генерация по валидному плану — действие workflow/tool.

Входы фиксируются на точных версиях; каждому специалисту доступны сами нужные тексты/материалы, а не только их идентификаторы. Наличие файла не заменяет approval.

| Этап / роль | Необходимые входы | Результат и условие перехода |
|---|---|---|
| Препродакшн / Producer | Идея, ответы автора, выбранные референсы; текущая Brief revision при изменении | После опроса — полный Brief; дальнейшие изменения создают новые revisions. При пробелах — вопросы в беседе. |
| Подтверждение брифа / автор | Точная Brief revision: история/замысел, персонажи, локация, стиль, длительность, число шотов, image width/height/aspect, качество видео; ComfyUI default или явный fal.ai | Сохранённое подтверждение версии и разрешение запуска. Неопределённые обязательные параметры блокируют старт. |
| Storytell / Agent → Review | Подтверждённый бриф и выбранный сюжетный контекст | Полная история и упорядоченные шоты с устойчивыми ключами, действием и начальным/конечным состоянием; approval точной истории. |
| Wardrobe / Agent → Tool → Review | Полный Brief, **полная approved Story**, её персонажи/локации и visual refs | План трёх anchors и кандидаты; выбор совместимого полного набора и его approval. |
| Storyboard / Agent → Tool → Review | Полный Brief, **полная approved Story** и выбранные approved anchors | План начального кадра каждого шота, кандидаты frames в порядке истории; выбор полного набора и approval. |
| Filmmaker / Agent → Tool → Review | Полный Brief, **полная approved Story**, выбранные approved frames и необходимые совместимые refs | План движения/камеры, кандидаты непрерывного клипа на каждый шот; выбор полного набора videos и approval. |
| Montage / Tool | Все выбранные approved clips в порядке истории и согласованные параметры выхода | Детерминированные склейки и необходимая техническая нормализация, проверенный финальный MP4 без звуковой дорожки. |

Для MVP набор anchors фиксирован: **один portrait, одна location, один character_sheet**. Portrait и location — txt2img; sheet — img2img с двумя exact inputs `[portrait, location]`. Это три logical units, не ограничение числа дополнительных дублей. Смена любого родителя требует совместимого нового sheet. Модели/workflows и mapping старого `background` в `location` описаны только в [render](hermes-kinodel-render.md#comfyui-профиль-по-умолчанию).

Frame показывает начало действия шота; video развивает это действие без внутренних склеек. Обязательные references не отбрасываются ради ограничений провайдера: несовместимый запрос блокируется с причиной. Число шотов, длительность и настройки не меняются агентом молча. Дубли одного результата — альтернативы; зависимость допустима только от реально используемого входа, не от соседнего дубля по порядку отображения.

## Состояния и продолжение

Ниже понятные пользователю состояния, **не готовая API enum**. Разрешённые действия определяет backend по сохранённым фактам.

| Состояние | Разрешённый переход / поведение Continue |
|---|---|
| Препродакшн / нужны уточнения | Producer собирает ответы, затем сохраняет Brief; изменения — новые версии, запуск после подтверждения точной revision. |
| Ожидание входов | Показать недостающую утверждённую версию или материал; Continue не обходит зависимость. |
| Готов к работе | Начать объявленный этап с фиксированными входами в пределах явного разрешения. Обычные переходы могут выполняться автоматически, без клика на каждой границе. |
| В работе | Показать прогресс; повторный Continue не создаёт ещё одну работу. Отмена — только если доступна. |
| Ожидание рендера / частичный набор | Проверять существующие заказы и показывать X/N; не отправлять весь набор заново. |
| Остановлен, можно продолжить | Continue продолжает ту же незавершённую работу с сохранёнными входами и разрешением, если доступен проверенный механизм восстановления. |
| Требуется review | Выбрать кандидаты и явно Approve либо отправить feedback; Continue не подменяет согласование. |
| Утверждён / завершён | Допустим только объявленный следующий этап при готовых входах и разрешении; завершённая работа не открывается заново. |
| Ошибка / отменён / заблокирован | Показать причину и конкретное разрешённое восстановление или новое производство. Не выполнять скрытый restart или оплаченный retry. |
| Неизвестен результат команды / reconnect | Сверить сохранённую операцию и заказ; повтор доставки не означает новую генерацию. |
| Final | Просмотр, скачивание и история; Continue не создаёт новый фильм. |

Continue не обновляет лимиты попыток/стоимости. Review approval не даёт неограниченного разрешения на downstream-генерацию. Истёкшее разрешение или неопределённость требуют явного решения до нового вызова.

### Простые правила допуска и остановки

Backend разрешает `required_input` в точные входы и проверяет решения человека из `required_approval`. Перед dispatch также проверяются остановка производства, разрешение работы и отсутствие дубля операции. `next` обозначает следующий этап маршрута.

| Работа | `required_input`: основные материалы | `required_approval`: решения автора |
|---|---|---|
| Storytell | Brief | Brief |
| Wardrobe | Brief + Story | Brief + Story |
| Anchor render | AnchorPlan + frozen settings; для sheet — exact portrait/location | Нет отдельного approval плана/родителей внутри anchor generation |
| Storyboard | Brief + Story + совместимый набор anchors | Brief + Story + набор anchors |
| Frame render | FramePlan + frozen settings + exact parents каждой unit | Используемый набор anchors; earlier frames внутри генерации не требуют отдельного gate |
| Filmmaker | Brief + Story + полный набор frames | Brief + Story + набор frames |
| Video render | VideoPlan + frozen settings + exact frame каждого клипа | Используемый набор frames |
| Montage | Полный набор clips в Story-порядке + output settings | Набор clips |

Это краткая таблица основных материалов; полные поля и источники задаются картой этапа и schema, включая context/profile guidance. Все approvals проверяются на версии, закреплённые в inputs. Разрешение render-операции сохраняется независимо от отсутствия отдельного review её плана.

Статус Kanban сообщает о lifecycle task, но `done` не заменяет эти условия. На предоставленном скриншоте видны triage/todo/scheduled/ready/running/blocked/review/done. Их точный mapping проверяется в установленном Hermes: ожидание родителя, таймера, пользователя и provider — разные причины ожидания. `scheduled` нельзя считать универсальным состоянием рендера. Новые Kanban-статусы для Kinodel не требуются.

**Остановка производства:** сохраняет запрет новых dispatch, render submits и переходов. Backend запрашивает остановку активной работы поддержанным способом; уже принятый provider job может закончиться позже. Поздний результат сохраняется без автопродолжения и approval. Продолжение требует явного действия автора и проверки незавершённой работы; повторный клик/reconnect запрет не снимает.

**`question` — вопрос автору:** сохранить вопросы к попытке, показать в панели этапа/Producer и завершить turn без revision. Ответ передаётся через feedback/rework: новая попытка той же task с прежними exact inputs и сохранённым feedback. Если ответ меняет утверждённый upstream input, применяется правило его правки. Вопрос не расходует schema-repair retry. Конкретный host-вызов rework уточняется в Hermes.

**Предложение разрешения первого прохода:** подтверждение Brief разрешает одну первоначальную творческую работу каждого этапа и одного кандидата на каждую обязательную unit, с остановками на review. Для невалидного output — до трёх дополнительных repair-попыток в пределах host-лимитов. Request changes и Generate явно разрешают новую ограниченную работу; число творческих revisions не ограничивается тремя schema retries. Платные provider retries не выводятся из этой политики автоматически.

## Правки и версии

На текущем review замечания получает владелец этапа: Storytell, Wardrobe, Storyboard или Filmmaker. Он читает предыдущий полный результат, точные входы и feedback и возвращает **новую полную версию**. При нехватке данных запрашивает уточнение; старый результат остаётся доступен. Новая версия снова требует review.

Ручной render создаёт новый candidate из видимых prompt/seed/settings без LLM; автоматический render специалиста проходит тот же контролируемый путь. Technical retry повторяет техническую попытку, а не переписывает творческий план. Selection фиксирует дубль, approval — полный совместимый результат этапа.

Если изменяемый результат уже закреплён в prepared input зависимой операции, требуется новое производство с явной связью с исходным — даже до запуска следующего worker. До этой границы можно явно переоткрыть review в том же производстве. Старые результаты и решения сохраняются; точные правила — [граница правки](hermes-artifact.md#граница-правки-фиксация-входов-следующей-операции).
