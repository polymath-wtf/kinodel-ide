# Roadmap cinematic MVP

**Сейчас: препродакшн.** Выбран фиксированный workflow на Hermes Kanban; конкретная интеграция ещё не реализована. Это короткая последовательность работ, не календарь. Определение готового продукта — [MVP](hermes-mvp.md).

## Этап 1. Подготовка и backend

### 1.1. Пакет контекста
- [ ] Согласовать документы и инструкции пяти ролей.
- [ ] Подготовить доступные workflow-файлы, mappings и UI-референсы.
- [ ] Перенести пакет в целевой Hermes с рабочими ссылками на источники.

### 1.2. Уточнение механизмов Hermes
- [ ] Зафиксировать version/commit и сопоставить [открытые вопросы](hermes-questions.md) с API и исходниками установки.
- [ ] Выбрать запуск локального пакета, host lifecycle, storage, permissions и scopes config.
- [ ] Подтвердить приём результата, human review/rework и связь с worker session.
- [ ] Проверить capabilities ComfyUI: Qwen inputs/geometry и MiniMax geometry/duration/audio.

### 1.3. Запуск backend плагина
- [ ] Подключить host и Kanban board/profiles; сохранять связи project/task/run/session.
- [ ] Подключить хранение проекта, путь команд и чтения для UI.
- [ ] Реализовать общий допуск по required_input/required_approval, validation и публикацию результатов.
- [ ] Проверить штатный запуск/приём результата task и restart без дублирования задач.

**Готово:** локальный backend работает на выбранных механизмах Hermes; ближайший агентный этап можно подключить без нового runtime.

## Этап 2. Producer → подтверждённый Brief

### 2.1. Рабочее пространство
- [ ] Подготовить минимальную React-оболочку: проект, Producer chat и панель Brief.
- [ ] Связать проект с Producer session, событиями и сохранённой историей.

### 2.2. Агент и данные

- [ ] Передавать capabilities/defaults; собирать одного героя, одну локацию, шоты и render settings.
- [ ] Сохранять полные Brief revisions и показывать точную версию перед подтверждением.

### 2.3. Подтверждение

- [ ] Проверить повторное открытие проекта и восстановление актуального Brief после restart.

**Готово:** автор обсуждает идею и подтверждает полный валидный Brief.

## Этап 3. Storytell → готовая история

### 3.1. Запуск специалиста
- [ ] Подключить Storytell profile, StoryInput/StoryOutput schemas и точные bindings.
- [ ] Создавать Kanban task только по подтверждённому Brief.
- [ ] Валидировать полный Story, IDs, покрытие шотов, порядок и длительности.

### 3.2. История и review
- [ ] Показывать полный Story, версию, происхождение и состояние task.
- [ ] Подключить question/ответ и правку через feedback/rework той же task.
- [ ] Сохранять новые revisions и approval точной Story.
- [ ] Проверить restart, повтор команд и запрет downstream по одному native done.

**Готово:** автор получает историю, дорабатывает и утверждает её; данные восстанавливаются после restart.

## Этап 4. Wardrobe → anchors

### 4.2. Render-путь

### 4.3. Выбор и review

## Этап 5. Canvas → панель раскадровки

### 5.1. Структура доски
- [ ] Создать Canvas с группой anchors и группами шотов в порядке approved Story.
- [ ] Для каждого shot_id подготовить места для image frames и MP4 clips, их кандидатов и выбранных версий.
- [ ] Подключить данные существующих anchors и пустые состояния будущих frames/clips.
- [ ] Показывать реальные зависимости; альтернативные дубли отображать рядом.

### 5.2. Карточки и инспектор
- [ ] Подготовить preview изображений и MP4 playback, открытие originals и media metadata.
- [ ] Подключить общий инспектор inputs/output, prompts/settings, parents, версий и происхождения.
- [ ] Подготовить Generate, Select и review-действия по разрешениям backend.
- [ ] Отображать render progress, частичные наборы, ошибки и недоступные originals.

### 5.3. Подключение данных
- [ ] Связать карточки с production/shot/unit/candidate refs и чтением сохранённых media.
- [ ] Проверить на подготовленных данных размещение images и MP4, выбор и возврат после reload.
- [ ] Проверить навигацию, inspector focus и сохранение выбранного материала между представлениями.

**Готово:** доска принимает frames и MP4 по стабильным shot IDs; следующие агенты заполняют уже подготовленные места.

- [ ] Проверить финальный MP4: размеры, длительность и отсутствие audio stream.
- [ ] Сохранить рецепт, source refs и original финала; подключить просмотр и скачивание.

### 8.2. История и целостный UX
- [ ] Завершить Pipeline, переходы между представлениями и историю revisions/candidates/производств.
- [ ] Подключить новый запуск из исторического Brief и позднюю редакторскую Story без изменения прежнего фильма.
- [ ] Пройти весь путь на ComfyUI: один герой, одна локация, два шота и четыре review.

**Готово:** автор проходит весь cinematic от идеи до проверенного немого MP4. fal.ai проверяется отдельно и не блокирует первую приёмку; два шота — размер примера, не ограничение продукта.

## Ближайшие уточнения

Зафиксированы один герой/одна локация, раздельные defaults image 1024×1024 и video 480×480, остановка новых работ при Stop и максимум три дополнительных retries невалидного output. [Пять минимальных агентных промптов](../hermes-agents/README.md) подготовлены как текстовые инструкции, не активированные profiles. Поздняя редакторская Story сохраняется без применения к уже подготовленному производству; применение требует нового запуска. Контракт `question` и предложения разрешения первого прохода и plan → backend render описаны в доменных документах. Политика нового набора после изменения плана требует подтверждения. Исполняемые schemas и host integration пока не готовы.

- Проверить возможности выбранных ComfyUI workflows, особенно Qwen geometry и MiniMax duration/audio. Portrait, location и зависимый от обоих character_sheet — уже принятое решение.
- Довести [input/output схемы](hermes-artifact.md#что-уточнить-перед-исполняемыми-json-schemas), покрытие истории и правила revise до исполняемой проверки.
- Внутри Hermes определить механизм переходов, task/tool-wait/review, публикацию результата, storage и tools restrictions — [очередь вопросов](hermes-questions.md).
- Пользователь проверил worker-session resume; уточнить конкретный способ вызова и различие «Вопрос» / «Правка», затем подключить к UI.

Детали реализации уточняем для ближайшего этапа после проверки host-механизмов. Свидетельства выполненных проверок хранятся в [test-results](../../../test-results/README.md), а здесь — текущий статус и дальнейшие работы.
