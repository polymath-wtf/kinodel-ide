# Нодовый интерфейс: минимальная архитектура

Статус: **целевой продукт принят; правила ниже предложены для проверки. Исполняемый конструктор ещё не реализован.**

## Зачем это User

User собирает производство из видимых этапов: история, подготовка персонажей и локаций, кадры, видео, монтаж. Каждый этап можно открыть, посмотреть полученные материалы, изменить инструкции и сравнить результаты. Готовый cinematic остаётся стартовым шаблоном; собственные цепочки строятся из тех же элементов.

Сейчас описаны заранее заданные маршруты. Цель — сначала показать их нодами, затем разрешить настройку и сборку собственных маршрутов. Это общее направление продукта; конкретная схема и инструкции принадлежат проекту, их изменение не меняет чужие проекты или историю запусков.

## Что видит пользователь

- В центре — схема с соединениями, статусами и превью результатов.
- Внутри ноды — входы, инструкции, обсуждение, результат и предыдущие попытки. Следующему этапу передаётся выбранный материал, а не вся переписка.
- Несколько этапов позднее можно свернуть в составную ноду, например «Подготовить персонажей и локации». Внутренние согласования остаются видимыми и обязательными.

## Минимальные правила

| Понятие | Правило | Пример |
|---|---|---|
| Тип ноды и её экземпляр | Один тип можно добавить несколько раз; у каждого экземпляра собственные входы, результаты и история | Два сценариста предлагают разные истории |
| Порт | Именованный вход или выход с назначением, модальностью и количеством материалов | Несколько референсов внешности, один стартовый кадр |
| Соединение | Передаёт конкретный результат в конкретный вход; порядок исполнения выводится из зависимостей | Storyboard ждёт утверждённые якоря |
| Владелец результата | Каждый результат создаёт один экземпляр ноды; другой создаёт свою версию в своём выходе | Редактор не перезаписывает результат сценариста |
| Источник | Предоставляет выбранную версию текста, файла или чанка без вызова модели | Character chunk с внешностью героя |
| Согласование | Человек утверждает точный результат или выбирает полный набор кандидатов | По одному изображению для каждого требуемого якоря |
| Версия схемы | Запуск фиксирует соединения, инструкции, модели, workflow и выбранный контекст | Изменение промпта не меняет уже отправленный рендер |

Одинаковой модальности недостаточно для соединения: история не является промптом кадра, кандидат не является утверждённым изображением. Перед запуском проверяются обязательные входы, назначение материалов, количество референсов, возможности моделей и генераторов, а также согласования. Ошибку показываем на конкретной ноде до платного вызова.

## Кто выполняет работу

Агент рассуждает и возвращает проверяемый творческий результат. Сервис генерирует или обрабатывает медиа. Граф определяет порядок и ожидания. Хранилище сохраняет результаты и версии. Человек утверждает творческий выбор.

Интерфейс отправляет команды серверу и показывает подтверждённое состояние. Закрытие браузера не отменяет принятую работу. После перезапуска состояние восстанавливается из сохранённых данных, а не из истории сообщений.

Сначала используем существующие заранее описанные графы LangGraph. Для конструктора добавляем минимальный перевод проверенной схемы из известных типов нод в исполняемый граф. Пользовательская нода на первом этапе — настройка известного типа агента с объявленными входами и выходом, а не произвольный код. Агент не выбирает следующую ноду через текст или `/goal`.

Первые пользовательские схемы идут вперёд по зависимостям без произвольных циклов. Исправление через Critic и владельца результата — заранее заданный ограниченный маршрут согласования. Параллельные ветки и вложенные схемы включаются отдельным этапом.

## Изменение и повторный запуск

Технический повтор продолжает ту же операцию с теми же входами. Потерянный ответ генератора сначала сверяется с состоянием задания; повторная отправка не считается безопасной автоматически.

Редактирование инструкций, контекста или соединений самой схемы создаёт её новую версию и новый запуск по явному действию человека. Старые результаты доступны для сравнения. Переиспользование между версиями схемы включается только после проверки совместимости и зависимостей; исправление якорей на текущем review описано ниже.

На review якорей творческая правка идёт через Critic к Wardrobe; перегенерация с новым seed — прямо в Render. Пересоздаются изменённые якоря и зависящие от них изображения: новое лицо требует нового sheet, новая location сохраняет лицо и sheet. Неизменённая независимая location сохраняется при замене лица. Затем человек снова проверяет полный набор. Исправление кадров идёт к Storyboard и не меняет якоря скрыто; для изменения уже утверждённых предков нужен новый запуск.

Маршрут: Wardrobe plan → Render anchors → review полного набора с сохранением выбора в `main_frames` → Storyboard, использующий утверждённые изображения по ролям. В первом примере Render последовательно создаёт `hero_face`, затем `hero_sheet(hero_face)`, затем независимую `location` без персонажей. Промежуточного выбора нет. Сохранение утверждённого выбора — часть review, без отдельной пользовательской promotion-ноды.

## Граница с генераторами

Один сложный workflow ComfyUI показывается одной сервисной нодой с объявленными входами и выходами. Подключение подставляет параметры, передаёт медиа, отслеживает задание и сохраняет проверенные результаты. Агент не управляет внутренними техническими узлами workflow.

Внешний HTTP-сервис подключается по тому же правилу: известные входы/выходы, авторизация, получение статуса, обработка повторов и ошибок. Обратное уведомление лишь помогает обнаружить завершение; оно само не утверждает результат. Секреты и адреса служебных подключений не попадают в творческие инструкции.

## Что нужно согласовать и проверить

1. Минимальную палитру и ограничения первого конструктора из [каталога нод](node-list.md).
2. Новый маршрут якорей на одном примере: портрет, полный рост, локация → кадр с несколькими референсами.
3. Точные формы сохраняемых данных, маршруты исправления и возможности выбранного workflow до исполнения.

Точный маршрут и правила зависимостей закреплены в [cinematic](cinematic.md). Их реализация и проверка на рабочем примере остаются задачами [плана разработки](node-roadmap.md).
