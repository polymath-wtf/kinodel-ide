# Архитектура данных Kinodel

Обновлено: **21 сентября 2026**. Принятые границы и рекомендуемое размещение; прикладная SQL-схема и восстановление Kinodel ещё не реализованы. Проверенная совместимость библиотек и единственный план первого билда — [Local MVP](../roadmap-mvp.md).

## Целевая форма

**Одна прикладная SQL-база + отдельно управляемые checkpoints LangGraph + хранилище неизменяемых файлов.** Библиотека знаний использует эти же механизмы. Поиск — необязательное производное представление, а контекст — подготовленный вход конкретной операции, не ещё одна база.

| Ответственность | Локальное приложение | Hosted, отдельный этап |
|---|---|---|
| Проекты, версии, решения, работа, задания; позднее библиотека и чаты | SQLite | PostgreSQL |
| Позиция графа, задачи и ответы на паузах | `AsyncSqliteSaver`; рекомендуем отдельный SQLite-файл в том же data root | `AsyncPostgresSaver`; отдельно управляемая схема в том же PostgreSQL deployment |
| JSON результатов, изображения, видео, аудио; позднее исходники и wiki-снимки | Managed files | Private server/object storage; GCS принят для удалённого render endpoint |
| Поиск по разрешённой библиотеке, позднее | Сначала прямые ссылки, затем полнотекстовый индекс | То же; vectors только после оценки пользы |
| Вход и сервисные кредиты, позднее | Без аккаунта; подключение к сервису не переносит проект | Supabase Auth и серверный журнал расчётов |

Это разделение владельцев данных, не требование отдельных серверов. В локальной установке одна прикладная база обслуживает проекты владельца, не новая БД на фильм или агента. Hosted не требует БД на пользователя. Два профиля разделяют правила, но не SQL, блокировки или автоматическую синхронизацию.

## Один владелец факта

| Факт | Источник истины | Что не заменяет его |
|---|---|---|
| Проект, доступ, запуск, принятая команда, отмена и окончательный исход | Прикладная БД | Имя папки, ответ HTTP, статус в браузере |
| Где продолжать граф | Checkpointer, включая pending writes | Самодельная таблица маршрутов |
| Точная версия результата | Неизменяемые байты + метаданные БД | Перезаписываемый файл или тело в checkpoint |
| Текущий результат этапа | `execution_bindings` | Последний созданный файл |
| Что человек утвердил | Точный subject/selection и receipt применения решения | Успешная генерация или завершение фильма |
| Что получил агент | Подготовленная `operations` с exact inputs и `ContextSelectionV1` | Новый поиск при retry, весь разговор |
| Повторно используемая творческая память | Typed artifact + утверждённый `chunk_bindings` | Поисковый отрывок, embedding, пересказ чата |
| Знание wiki | Опубликованная Markdown-ревизия с источниками и правами | Рабочая копия редактора |
| Разговор | Принятые feedback/ответы; позднее прикладная история чатов | Состояние производства |
| Оплата сервисного заказа | Серверный журнал расчётов | Локальный баланс или стоимость провайдера |

## LangGraph В Этой Модели

- **Checkpointer используем:** сохраняет thread одного execution, его паузы и незавершённые задачи. Не сохраняет за нас согласованно файлы, решения и внешние заказы.
- **State держим компактным:** IDs и точные refs. История сообщений, медиабайты и вся библиотека туда не входят.
- **Runtime context используем для зависимостей:** проверенная личность, сервисы, текущий fence. При resume приложение передаёт их заново; это не сохранённый prompt.
- **Store не обязателен:** это интерфейс cross-thread key-value памяти, а не требование второй канонической БД. Наши chunks уже доступны между executions через библиотечные bindings и обычные функции чтения. `store.put` не заменяет approval, версионирование, проверку прав и атомарный commit.
- **Time travel не откатывает проект:** диагностический replay может повторять вызовы. Пользовательская творческая альтернатива — отдельный [Fork](../hilp/fork.md), после MVP.

Если будущая интеграция действительно потребует `BaseStore`, определить один источник истины для её данных. Для поиска допустима перестраиваемая проекция; двойная запись canonical chunks в Project DB и Store не нужна. Namespace организует ключи, но сам по себе не авторизует пользователя. Сверка механизмов и оговорки к приложенным примерам — [источники](source-coverage.md).

## Состав По Мере Включения Функций

Точный логический инвентарь принадлежит [implementation](../backend/implementation.md#project-db-tables). Идентичности, ограничения и рабочие выборки — SQL columns; bounded typed inputs/results — JSON; большие неизменяемые тела и медиа — файлы. Не нужны таблицы для каждого shot, поля персонажа или типа chunk.

Первый пользовательский MVP включает **видео и монтаж**, поэтому jobs, attempts, selected assets и group waits входят в реализацию. Текстовый проход — промежуточная проверка. Node discussion использует review feedback и ответы операций. Общий чат, публикация памяти, wiki, поиск, hosted-аккаунты и кредиты включаются позднее; старые обозначения «MVP credits» означают будущий сервисный этап.
