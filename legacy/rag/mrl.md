# Спецификация Архитектуры Эмбеддингов: Токены, Векторы и MRL

При проектировании универсальных эмбеддингов для RAG-систем необходимо различать ограничения на входные данные (контекст) и характеристики выходных данных (векторное пространство).

## 1. Токенизация и Контекстное Окно (Входные данные: 8192)
* **Суть:** Это пропускная способность модели на чтение. 
* **Определение:** Токен — это базовая единица данных (часть слова, целое короткое слово или спецсимвол), на которые разбивается исходный текст перед подачей в нейросеть.
* **Значение 8192:** Максимальное количество токенов, которое модель способна обработать в рамках одного запроса. Это эквивалентно примерно 6000–8000 слов. 
* **Применение в RAG:** Это лимит размера одного "чанка" (куска текста), который вы отправляете на векторизацию. Оптимальный размер чанка обычно меньше лимита (например, 512-1024 токена) для сохранения высокой плотности смысла.

## 2. Размерность Вектора (Выходные данные: 3072)
* **Суть:** Это "разрешение" или "детализация" семантического отпечатка.
* **Определение:** Вектор — это массив чисел (координат), в который нейросеть сжимает весь смысл прочитанных токенов. 
* **Значение 3072:** Базовая размерность модели. Это значит, что смысл входного текста описывается 3072 уникальными координатами в многомерном пространстве. Чем выше размерность, тем точнее модель улавливает тончайшие нюансы, сарказм или сложную техническую терминологию.
* **Применение в RAG:** Это размер массива чисел, который будет сохранен в вашей векторной базе данных (например, Qdrant, Pinecone или pgvector).

## 3. Matryoshka Representation Learning (MRL)
* **Суть:** Технология динамического сжатия размерности вектора (Output) без необходимости переобучения модели.
* **Как это работает:** Алгоритм MRL обучает модель концентрировать наиболее важную, фундаментальную семантическую информацию в **первых измерениях вектора**. Подобно матрешке, компактное представление "спрятано" внутри более крупного.
* **Практическая польза:** Вы можете программно "отрезать" хвост вектора (сделать срез массива), уменьшив его с 3072 до меньшего значения. Это позволяет гибко балансировать между потреблением памяти, скоростью поиска и качеством:
    * **3072 (Максимальная точность):** Хранит 100% информации. Используется для критически важных задач, где важны малейшие нюансы контекста. Требует максимум RAM в векторной БД.
    * **768 (Сбалансированный режим):** Стандарт отрасли. Сохраняет ~98% семантической точности базового вектора, но экономит до 75% памяти и значительно ускоряет поиск.
    * **256 (Сверхбыстрый режим):** Максимальное сжатие. Экономит более 91% памяти. Идеально подходит для первичного, грубого поиска (First-pass retrieval) по огромным массивам данных, результаты которого затем можно пропустить через Cross-Encoder (Reranker).

## 4. Synapse policy

В Synapse MRL применяется не к размеру нейрона, а к **embedding profile**.

Один и тот же нейрон может иметь несколько профилей:

| Profile | `output_dimensionality` | Роль |
|---|---:|---|
| `first_pass` | 256 | быстрый recall по всему vault |
| `default_retrieval` | 768 | основной поиск по markdown/project memory |
| `deep_rerank` | 1536 | rerank сложных multi-domain задач |
| `full_fidelity` | 3072 | multimodal/story/vibe/R&D, где важны нюансы |

Каскад поиска:

```text
exact/path/metadata filters
-> 256 first-pass vector search
-> 768 candidate retrieval
-> 1536/3072 rerank when needed
-> LLM synthesis
```

Главное правило: размерность query vector должна совпадать с размерностью index vector. Для одновременного быстрого и полного поиска нужны либо full 3072 vector + prefix slices, либо отдельные индексы/колонки `vector_256`, `vector_768`, `vector_1536`, `vector_3072`.
