# Локальный менеджер аккаунтов Codex — план реализации

Дата исследования: 2026-09-17. Целевая среда: Windows, OpenCode 1.18.31, Node.js 22.17.0.

## 1. Назначение и статус

Пользователь вручную выбирает одну из своих подписок ChatGPT/Codex для работы в OpenCode, не проходя вход заново при каждом переключении. OpenCode выполняет авторизацию и обновляет доступ; наша утилита хранит подписанные сохранённые входы и переключает их между запусками OpenCode.

Это согласованный предпроизводственный план для продолжения в новом чате. Менеджер ещё не реализован. Проверка совместимости выполнена по исходникам релиза; практическая проверка штатного входа без вмешательства multi-auth ещё предстоит. Нельзя объявлять совместимость полностью проверенной до выполнения этапа 1.

Пользователь просит двигаться по этапам. Реализация менеджера и отключение действующего плагина — разные этапы. Отключение multi-auth допускается только после успешной приёмки и отдельного согласования.

## 2. Решение и границы

- Небольшая локальная CLI-утилита, рабочее имя `oca`, на установленном Node.js. Без сборки и сторонних зависимостей, пока не доказана необходимость.
- Поддерживаем штатную legacy-авторизацию OpenCode 1.18.31: один текущий OAuth credential для `openai`.
- Переключение между запусками OpenCode. Горячее переключение и одновременная работа разных проектов под разными аккаунтами не поддерживаются первой версией.
- Выбор относится ко всему локальному профилю OpenCode, а не только к Kinodel.
- Не реализуем OAuth, PKCE, refresh, отправку запросов моделям, автоматическую ротацию, cooldown, мониторинг квот, dashboard, демон или собственный сервер.
- Каталог моделей — отдельная задача. Менеджер аккаунтов не должен заниматься discovery моделей.
- Не строим универсальную систему адаптеров legacy/V2 и не синхронизируем два хранилища авторизации.
- Неизвестный или неподдерживаемый режим должен приводить к понятному отказу от изменения, а не к угадыванию.

## 3. Что проверено: legacy и V2

Локальная команда `opencode --version` вернула `1.18.31`. Ниже выводы по исходникам тега `v1.18.31`, а не обещание поведения любой будущей версии.

| Область | Подтверждённый факт | Следствие |
|---|---|---|
| Legacy Auth | OAuth содержит `type`, `refresh`, `access`, `expires`, необязательные `accountId`, `enterpriseUrl`; запись хранится по provider ID | Можно сохранять и восстанавливать текущую запись `openai`, сохраняя остальные данные |
| Источник legacy | Используется `Global.Path.data/auth.json`; `OPENCODE_AUTH_CONTENT` имеет приоритет при чтении | Нельзя безусловно полагаться на домашний путь или объявлять файловое переключение действующим при внешнем переопределении |
| V2 SDK | Есть `/api/integration`, подключение OAuth и операции удаления/переименования `/api/credential/{credentialID}` | Само слово V2 не означает наличие переключателя нескольких аккаунтов |
| V2 Credential | Создание credential удаляет предыдущие credentials той же integration в транзакции | В этом релизе создание нового входа не является добавлением в многоаккаунтный pool |
| V2 Integration | Доступ хранится через Credential service и обновляется через него; активное connection выбирается из доступных connections | Редактирование legacy-файла не является доказанным способом переключить V2 |
| Проектная спецификация V2 | Описывает `/api/auth` и активацию аккаунта | Не путать проектируемый контракт с реализованным API релиза |

В предыдущем исследовании текущий исходник встроенного Codex-плагина подтвердил штатные browser/device login, refresh и сохранение обновления через OpenCode. Точную цепочку этого плагина в установленном релизе необходимо дополнительно проследить и проверить на этапе 1.

**Поддержка V2 в первой версии не заявляется.** Наличие V2 рядом с legacy само по себе не причина отказа: нужно установить, какой механизм обслуживает конкретный запуск. Если фактический путь не удалось подтвердить, запись запрещена. Способ такой проверки — результат этапа 1, а не уже реализованная гарантия.

## 4. Что заимствуем у Hermes

Из credential pools Hermes берём разделение авторизации и выбора аккаунта, сохранение обновлённого refresh token и необходимость координации изменений. Не переносим автоматическую ротацию, обработку квот и их инфраструктуру параллельной работы.

Главный принцип: OpenCode мог обновить refresh token; перед уходом с текущего аккаунта нужно сохранить последнюю запись. Нельзя восстанавливать старую копию поверх более свежего доступа.

## 5. Пользовательские команды

| Команда | Контракт |
|---|---|
| `oca add <name>` | Сохранить текущий известный вход, запустить штатный вход OpenCode, проверить и сохранить результат под именем |
| `oca save <name>` | Сохранить уже выполненный вход; не является заменой безопасного сопровождаемого добавления |
| `oca list` | Показать имена и фактическое совпадение текущего входа с сохранённым; секреты не выводить |
| `oca use <name>` | Сохранить свежий доступ текущего аккаунта и выбрать указанный |
| `oca next` | Тот же алгоритм переключения, выбор по стабильному порядку добавления; после последнего — первый |

Точный синтаксис штатной команды входа проверить через help установленной сборки. Не считать прежний пример `opencode auth login --provider openai` подтверждённым CLI-контрактом.

Неизвестное имя, пустой список и повреждённые данные дают понятную ошибку без записи. Выбор уже текущего аккаунта безопасен и не запускает авторизацию. Повторное добавление известного аккаунта предлагает обновить существующий вход; существующее имя не заменяется другим аккаунтом молча.

При отмене `add` прежний вход должен остаться доступным. Успешное добавление оставляет новый аккаунт текущим и сообщает об этом. Вход вне менеджера обнаруживается; он не должен автоматически записываться под старым именем.

## 6. Архитектура хранения

Два владельца данных:

1. **OpenCode** владеет текущей авторизацией и её обновлениями во время работы.
2. **oca** владеет именованными сохранёнными входами, обновляя их перед переключением или добавлением.

Предварительное расположение pool: пользовательский каталог конфигурации, отдельный файл менеджера. Точные пути, XDG overrides и Windows-права подтвердить на этапе 1. Секреты никогда не хранятся в репозитории.

Минимальная форма pool: версия формата и отображение `имя → credential` со стабильным порядком добавления. Отдельный обязательный указатель `active` **не нужен**: текущий аккаунт определяется по фактической авторизации OpenCode.

Сохранять целиком валидную OAuth-запись, а не конструировать урезанную копию из нескольких известных полей. Прочие providers и неизвестные поля исходного хранилища не удалять при изменении `openai`.

### Принадлежность аккаунта

Имя — пользовательская метка, не идентификатор. Совпадение email или `accountId` рабочего пространства само по себе не всегда доказывает одинакового пользователя. Access/refresh tokens меняются и также не являются постоянным идентификатором.

На этапе 1 определить достаточную стабильную идентичность по реальным форматам штатного входа, не выводя секреты. При неоднозначности запрещено автоматически перезаписывать именованную запись. Не придумывать универсальный JWT parser или поддержку всех провайдеров: нужен только проверенный случай Codex.

## 7. Минимальный безопасный алгоритм переключения

1. Проверить режим совместимости, отсутствие известных конфликтующих процессов и внешнего переопределения авторизации.
2. Захватить блокировку изменений самого менеджера. Две команды `oca` не могут писать одновременно.
3. Прочитать и провалидировать оба хранилища. Проверить существование цели до любых записей.
4. Определить, кому принадлежит фактический текущий вход. Неизвестный вход не затирать: предложить сначала сохранить его.
5. Сохранить свежую запись текущего аккаунта в pool надёжной заменой файла.
6. Повторно проверить, что исходная авторизация не изменилась с момента чтения; при конфликте остановиться. Эта проверка не устраняет все гонки с независимым OpenCode.
7. Заменить только текущую запись `openai` надёжной записью всего исходного документа.
8. Перечитать и проверить результат; лишь затем сообщить об успехе. Освободить блокировку.

Порядок **сначала сохранить текущий доступ, затем переключить** обязателен. Если шаг 5 не удался, шаг 7 не выполняется.

Отдельная транзакция между двумя файлами и журнал переключений не нужны для этого сценария: до замены остаётся прежний текущий вход, после — новый; отдельной потенциально ложной отметки `active` нет. Это должно подтверждаться тестами остановки между шагами. Не обещать стойкость к отключению питания только на основании использования rename.

Временные файлы должны иметь уникальные имена, закрытые права и находиться рядом с целевым файлом. Поведение замены на Windows проверить. Проверить освобождение блокировки после ошибки и поведение оставшейся блокировки после аварии, без небезопасного безусловного удаления.

### Ограничение конкурентности

Блокировка `oca` не управляет OpenCode. Проверка списка процессов — дополнительная защита, а не абсолютная гарантия отсутствия нового процесса через миллисекунду. Поддерживаемый контракт первой версии: пользователь завершил все экземпляры OpenCode, использующие этот профиль, и не запускает их до окончания переключения.

Не писать сложный диспетчер процессов ради обещания горячего переключения. Если даже для ограниченного Windows-сценария безопасную проверку нельзя сделать достаточно просто, остановиться и согласовать границу, а не скрывать её.

## 8. Текущее окружение и зависимости перехода

В предыдущих этапах установлен `@guard22/opencode-multi-auth-codex` 1.4.3. В его глобальной и cached-копиях вручную исправлялись URL Codex, возврат streaming response с заголовками и список моделей. Обновление пакета может затереть эти изменения.

Также добавлен проектный `.opencode/plugins/dynamic-codex-models.js`: он читает аккаунты multi-auth и добавляет видимые модели из каталога Codex. Это временная зависимость от старого плагина, не часть будущего менеджера.

Ранее успешно проверялись `gpt-6-astra` и `gpt-5.6-sol`, но **через исправленный multi-auth**, не через будущий менеджер и не как доказательство штатного пути.

В глобальной конфигурации ранее обнаружен сторонний OpenAI-compatible baseURL. При проверке штатного Codex нужно исключить его вмешательство в изолированной конфигурации. Значения ключей и OAuth credentials не читать в вывод и не публиковать.

В истории были два alias одного email; это повод проверить идентичность, а не автоматически удалять дубликаты.

Ранее агентские права запрещали чтение/изменение внешних каталогов. При отказе инструмента не обходить ограничение через shell, Node, другой путь или плагин. Запросить доступ либо дать пользователю выполнить конкретный шаг. Не менять собственные разрешения ради продолжения.

## 9. Этапы и критерии завершения

### Этап 1. Практическая совместимость — первый шаг нового чата

- [ ] Сверить фактические версии OpenCode и Node; если версия изменилась, пересмотреть релевантные исходники.
- [ ] Проверить встроенный Codex-плагин, legacy auth и связь с V2 в точном релизе.
- [ ] Определить фактические пути, overrides, идентичность аккаунта и права доступа Windows.
- [ ] Подготовить изолированную проверку, не выключая multi-auth в рабочем профиле и не запуская параллельный refresh одной копии credentials в двух местах.
- [ ] Подтвердить штатный вход, выполнение запроса и место сохранения обновлений.
- [ ] Определить простой проверяемый способ отличать поддерживаемый режим от неподдерживаемого.
- [ ] Отдельно проверить доступность нужных 5.6 и Astra. Если нужен фикс каталога — согласовать отдельный минимальный фикс.

Выход: краткий отчёт «подтверждено / не подтверждено / блокер». При несоответствии предпосылок не начинать файловый переключатель вслепую.

### Этап 2. Изолированный прототип

- [ ] Реализовать команды и алгоритм на вымышленных credentials в тестовых каталогах.
- [ ] Минимальная структура: CLI, тесты средствами Node, краткая инструкция. Без framework, server и новых runtime-зависимостей.
- [ ] Проверить валидацию, конфликт имён, идентичность, сохранение остальных providers и восстановление после прерывания.
- [ ] Не добавлять лишние настройки, абстракции, миграционные адаптеры и поддержку иных providers.

### Этап 3. Приёмка реальными аккаунтами

- [ ] Два аккаунта: вход, запрос, переключение A → B → A.
- [ ] Обновление доступа штатным OpenCode; после переключения и возврата сохранена свежая версия.
- [ ] Отмена добавления и самостоятельная смена входа вне менеджера.
- [ ] Нет секретов в выводе; фактический выбранный аккаунт определяется корректно.

Успешный единичный запрос не заменяет проверку refresh. Управляемую симуляцию и реальное подтверждение обновления отмечать отдельно.

### Этап 4. Подготовка и согласование перехода

- [ ] Согласовать способ переноса: предпочтительно штатный вход; импорт multi-auth — только отдельное явное решение с проверкой форматов и идентичности.
- [ ] Подготовить возврат конфигурации, не восстанавливающий устаревшие токены поверх свежих.
- [ ] Решить судьбу зависимого плагина каталога моделей.
- [ ] Получить отдельное подтверждение на отключение multi-auth.
- [ ] После отключения повторить запросы и переключение в рабочем профиле.

## 10. Минимальная матрица тестов

| Сценарий | Ожидаемый результат |
|---|---|
| Неизвестная цель, повреждённый документ, не-OAuth вход | Отказ без изменения исходных данных |
| Выбор текущего, один аккаунт и `next` | Безопасное предсказуемое поведение |
| Refresh изменил tokens | Свежая версия попадает в pool до переключения |
| Вход принадлежит другому пользователю | Нет перезаписи записи прежнего пользователя |
| Ошибка записи pool | Текущий вход не меняется |
| Прерывание до/после замены текущего входа | Можно определить реальный текущий аккаунт без `active` |
| Два одновременных переключения | Нет смешивания записей |
| Изменение исходных данных во время операции | Обнаруженный конфликт останавливает запись |
| Отмена/ошибка штатного входа при `add` | Прежний доступ остаётся восстанавливаемым |
| Прочие providers и неизвестные поля | Сохраняются |
| Авторизация из окружения или неподдерживаемый путь V2 | Нет ложного сообщения об успешном переключении |
| Windows: замена, права и оставшаяся блокировка | Проверено фактическое поведение, а не только POSIX-предположения |

## 12. Инструкция для следующего чата

Начать с этапа 1. Не считать проверку исходников end-to-end тестом. До доступа к внешним данным проверить разрешения; при отказе остановиться и запросить разрешённый способ работы. Не выводить секреты. Не отключать плагины рабочего профиля без отдельного согласования.

Объяснять пользователю результаты по `docs/EXPLAIN_FOR_PM.md`: сначала практический смысл и вывод, затем подтверждённые ограничения и следующее решение. Этот документ — технический handoff; пользовательские отчёты должны быть короче и без внутренних деталей.

Критерий простоты: менеджер выбирает аккаунт, OpenCode авторизует и обновляет доступ. Если реализация начинает отправлять запросы моделям, обслуживать собственный OAuth или синхронизировать legacy и V2 — остановиться: это выход за согласованный объём.
